TADA Studio Scheduler — Current State

As-Is architecture review Prepared by Vipul Sharma Source aicoe-tada-builder-app (24 Aug snapshot)

TADA Studio's cron-based workflow scheduler is fully implemented on the backend, but switched off in production behind a feature flag. Reading the code end-to-end surfaces two confirmed structural issues and one strong open question — most plausibly connected to the earlier platform outage this feature caused.

How a schedule runs today

02

Step-by-step, in the code

  1. A user calls PUT /api/schedules/workflow/{id} with a cron expression, timezone and active flag. The endpoint validates both before touching the database. backend/api/workflow/scheduling.py — update_workflow_schedule()
  2. The cron fields are written onto the existing published_workflows row — the same table used by the unrelated "publish workflow as public API" feature. There is no dedicated schedule table. backend/models/workflows/publishing/published_workflow.py
  3. The live, in-process scheduler is updated immediately so the change takes effect without a restart. scheduler_service.add_or_update_schedule()
  4. On every backend boot, startup code reloads every active schedule from the database into that process's own APScheduler instance — this runs per-process, with no awareness of any other replica. backend/app.py:184-190 → scheduler_service.initialize()
  5. When the cron time arrives, that process's APScheduler calls _execute_workflow() in a background thread, which hands off to the shared execution pool and returns immediately — it does not wait for the run to finish. scheduler_service.py — _execute_workflow()
  6. The run counter is incremented right after hand-off, not after completion — so it reflects "submitted," not "succeeded." scheduler_service.py — cron_run_count += 1
  7. The actual work runs on the same 10-worker thread pool that serves every editor click, chat message, and API call — scheduled and interactive traffic are never isolated. backend/api/graph/constants.py — THREAD_POOL_MAX_WORKERS = 10
03

What exists today

Full CRUD on a schedule (create, update, pause, resume, delete), a manual "trigger now" endpoint, cron and IANA-timezone validation, and a single environment-variable kill switch (SCHEDULING_ENABLED) that gates every endpoint behind a 503 when off — this is the literal mechanism behind the "Coming Soon" state in the UI. No code changes are needed to turn it on for Dev; just the env var and a restart.

Confirmed issues

Confirmed in code

No coordination between backend replicas. Every replica independently loads and fires the same schedules — a workflow scheduled once can run N times simultaneously if N replicas are running.

app.py:184-190, scheduler_service.py
Confirmed in code

Scheduled runs share one 10-thread pool with all live traffic. A burst of scheduled jobs can starve real users trying to run workflows in the editor at the same time.

constants.py — THREAD_POOL_MAX_WORKERS = 10
Confirmed in code

cron_run_count / cron_failure_count reflect submission, not actual outcome. A workflow can fail on every run and still show a clean success count.

scheduler_service.py — _execute_workflow()
Confirmed in code

No dedicated schedule table — cron state is bolted onto published_workflows, a table built for a different, unrelated feature (publishing workflows as public APIs).
