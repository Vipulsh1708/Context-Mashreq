3. WHY — VISHAL'S REASONING
--------------------------------------------------
**Ontology, as Vishal defined it:** the relationships and entities of the data — it captures the *intent*/context of data stored in the database. A single word/term can have multiple meanings depending on context (his example: "Amazon" could mean the company/application in one context, or something else — e.g. brand context — in another). The ontology is what encodes the rules for disambiguating that context.

**The hallucination/ambiguity problem he illustrated:** if an agent has access to a large repository (company performance, marketing strategy, user data, etc.) and is asked something like *"what is my quarterly performance and how is it impacting my marketing budget?"* — this is really two different things bundled together (quarterly/company performance results, AND marketing-budget impact). With a simple/naive retrieval strategy, the agent risks hallucinating or giving a "parody" (likely meant: a partial/incorrect blended) answer instead of a properly consolidated one, because it isn't tracking how these two contexts relate.

**Why a knowledge graph fixes this:** "everything is linked to everything" — data should be traceable back to its origin/context. E.g., a question about a product should be traceable to the items involved in that product, the customers connected to it, and so on — all of that relationship space should be trackable. This gives the agent much better context to plan its full response flow, leading to better answers (and better handling of concurrency, per Vishal, though the exact mechanism connecting knowledge graphs to concurrency was not elaborated in the call — UNCONFIRMED detail).
